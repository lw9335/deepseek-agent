Super-agent 拆解

让一个会写代码的 agent，成为能接住团队消息、安排多项工作、及时交付的系统。

一页纸看懂

  1. 把 agent 想成能读说明书并使用工具的同事：模型负责决定下一步，程序实际执行工具。
  2. 这份原型把工作分给餐厅式的“前台”Router 和“后厨”Worker：前台判断与派工，后厨各自完成一项任务。
  3. 团队消息先经过来源和授权规则，得到一张带范围的工单；已有工作的后续讨论能直接送到相应执行者。
  4. DeepSeek Harness（DSH）像操作系统，提供会话和工具；superagent 像应用，组织会话、保存工作状态并把结果送回原处。
  5. 文章还提出云端与用户设备分离等方向，而这个公开仓库是本地研究原型，学习时必须把愿景、实现和缺口分开。

01 · 问题

为什么一个聊天 agent 不够用

想象一个能干的员工：一边接电话，一边修打印机，还要记住上一通电话的要求。即使他更聪明，只要每次都等维修完成才接下一通电话，队伍仍会越排越长。

模型像能读懂任务的脑子，输入文字后生成回答或工具调用；工具像手边的螺丝刀，由程序执行读文件、运行命令等动作；把“判断—行动—看结果—再判断”反复连接起来，便得到常说的 ReAct 循环。这是帮助理解的通用模型；本仓库调用 DSH 提供的 agent 和 Session 能力，未在这里重新实现整个模型循环。

依赖宿主的 agent、Session 和工具服务，以及创建、装饰会话的调用： src/app/sessions.ts:2 · src/app/sessions.ts:140

文章设计 作者把瓶颈从“单次任务能否完成”移到“人能否跟得上多个任务”。摘要中的“一个人同时跟进 3—5 个活跃 Session”是作者观察，不是普遍上限。团队需要的是一个可持续联系的同事，而不是让人替每个小任务维护一个聊天窗口。

目标生活例子技术含义与边界
Continuous 连续上午在前台交代，下午电话追问还能接上跨事件保留工作关系；原型用工单、话题和订阅串起后续讨论
Efficient 高效后厨做一道菜时，前台继续接单分离路由与执行；多 Worker 按容量并行
Proactive 主动获准巡检后发现问题，先检查再通知观察外部事件，按预先写好的规则开始工作；默认观察模式不自动接推断任务
Persistent 持续值班交接读工作台账，不靠记忆重来持久化、重启恢复、外部检查；本地进程仍受机器在线状态约束
原型对应：会话创建、订阅扇出、Worker容量、状态保存与重启恢复，以及默认观察模式；后文分别展开。 src/app/sessions.ts:138 · src/core/intake.ts:38 · src/executor/dsh.ts:166 · src/app/store.ts:47 · src/core/assignments.ts:83 · src/policy.ts:83

单个同步循环的困难有三类：等一次长命令时后来的消息排队；多个工作的历史混在一个笔记本里，读到无关内容的机会增多；循环绑在本地机器上时，机器离线就没有执行者。它们都是结构问题。可以改造循环使它异步、拆分上下文并保存状态，因此不能把这些局限说成所有 agent 的必然性质。

本章小结

Super-agent 的目标是节省人的协调成本。把不同任务的状态、工具执行和对话组织清楚，才能让模型能力服务于持续工作。

03 · 概念与实验

五个模块怎样协同

3.1 前台和后厨：Router / Worker

前台接到“这一桌少了一双筷子”，先判断找谁处理；后厨负责菜品。让前台亲自炒完一道菜再接待下一桌，就会让所有顾客等待。
Router 是主 Session，评估消息、决定工单和路由；Worker 是某张 Ticket 的执行器 Session，拥有自己的执行目录和工作上下文。Ticket 像订单，是一单位获授权的工作；Assignment 像一次排班，把这张订单交给某个执行器实例。

3.2 快递分拣：事件、话题与两条路径

export function textPage(resource: string, text: string, offset: number, limit: number) {
  const end = Math.min(text.length, offset + limit)
  return { resource, offset, total_chars: text.length,
    next_offset: end < text.length ? end : null, text: text.slice(offset, end) }
}

10　风险、限制和开放问题
